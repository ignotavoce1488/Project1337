# Конспектъ / Slovech

Telegram-бот, Mini App и API для расшифровки аудио и конспектирования. Целевая схема: один Linux VPS, Docker Compose, Caddy HTTPS, один экземпляр каждого процесса. Python 3.12; зависимости зафиксированы в `uv.lock`.

## Архитектура

- `slovech/api/` — HTTP-адаптер: авторизация через подписанные Telegram initData, получение конспектов, аудио, DOCX.
- `slovech/bot_handlers/` — Telegram-адаптер: проверка входа, постановка задач, выдача документов.
- `slovech/worker.py` — обработка постоянной очереди; скачивание, FFmpeg, AI, сохранение результата, уведомление.
- `slovech/core/models.py`, `slovech/core/storage.py`, `slovech/core/documents.py` — схемы данных, репозиторий с проверкой владельца, общий экспорт DOCX.
- `slovech/ai/services.py`, `slovech/core/youtube.py`, `slovech/core/telegram.py` — интеграции с внешними сервисами.
- `web/` — браузерное приложение без сборки; персональные данные не сохраняются в localStorage.

SQLite WAL и общие локальные Docker volumes подходят выбранной схеме одного VPS. SQL-запросы параметризованы; список индексирован по владельцу и времени; история выдаётся страницами. Бот и worker имеют файловые блокировки от двойного запуска. Не масштабировать сервисы через `--scale`, не размещать SQLite на NFS. Для нескольких серверов потребуются PostgreSQL, внешнее хранилище аудио и распределённая очередь.

Очередь обеспечивает обработку **как минимум один раз**, максимум три попытки с задержкой. Источник задания уникален по chat/message ID; результат сохраняется с ID задания. После перезапуска worker возвращает незавершённые задания в очередь. Повторное уведомление редактирует исходное сообщение. Если worker аварийно завершился после обращения к AI, внешний запрос может повториться и повлечь повторную оплату. Гарантии exactly-once для внешних API нет. Недоступность Telegram-уведомления не удаляет уже сохранённый конспект.

## Локальный запуск

```sh
cp .env.example .env
# Для разработки: ENVIRONMENT=development, DOMAIN=http://localhost:8000.
# Указать BOT_TOKEN и GEMINI_API_KEYS для бота и worker.
uv sync --frozen --python 3.12
uv run uvicorn slovech.server:app --reload
# В отдельных терминалах:
uv run python -m slovech.bot
uv run python -m slovech.worker
```

FFmpeg и ffprobe нужны worker и устанавливаются в Docker-образе. Для локального HTTP просмотра можно использовать заголовок `X-Admin-Secret`; админ-доступ по умолчанию отключён. Для него нужны `ADMIN_USER_ID` и случайный `ADMIN_SECRET` длиной не менее 32 символов. Не передавать секреты в URL. Реальный Mini App необходимо открывать через HTTPS из Telegram.

## Развёртывание на VPS

1. Установить Docker Engine и Compose plugin. Практическая исходная конфигурация: 2 vCPU, 4 ГБ RAM, SSD; потребление и ёмкость проверить на реальных записях. Суммарные лимиты контейнеров заданы в Compose.
2. Настроить DNS A/AAAA домена на VPS, открыть входящие 80/443, обеспечить исходящий HTTPS к Telegram, Google и YouTube. Порт API 8000 наружу не публикуется. Подсеть `172.30.80.0/24` не должна конфликтовать с сетями VPS.
3. Скопировать исходники, создать `.env` из примера, поставить `ENVIRONMENT=production`, `DOMAIN=https://ваш-домен`, `BOT_TOKEN`, `GEMINI_API_KEYS`. Ограничить доступ к `.env`: `chmod 600 .env`. Значения в `.env` с `$` заключать в одинарные кавычки, чтобы Compose не интерполировал их.
4. Выполнить:

```sh
docker compose config --quiet
APP_VERSION=release-1 docker compose build
APP_VERSION=release-1 docker compose up -d
APP_VERSION=release-1 docker compose ps
curl --fail https://ваш-домен/ready
```

5. Указать адрес `https://ваш-домен/app` в настройках Mini App бота в BotFather. Для polling удалить ранее настроенный webhook штатными средствами Telegram, если он существует. Не запускать второй polling-процесс с тем же токеном.
6. Проверить на тестовых Telegram-пользователях: аудио → конспект → история → DOCX; второй пользователь не видит чужие записи. Отдельно проверить английское аудио и перевод, YouTube, перезапуск worker во время обработки, недоступность AI, восстановление backup.

Caddy получает и обновляет сертификаты автоматически при корректном DNS и доступных challenge-портах. Конфигурация доверяет forwarded-заголовкам только от фиксированного внутреннего адреса Caddy. Если перед ним добавляется CDN или другой proxy, схему доверия необходимо настроить отдельно. API не требует cross-origin CORS: Mini App и API используют один origin.

## Конфигурация и ограничения

`.env.example` описывает параметры. Значения окружения валидируются при старте. Пути `DATA_DIR`, `AUDIO_DIR`, `STATIC_DIR` в Compose переопределены на `/data`, `/audio`, `/app/web`.

- Публичный Telegram Bot API: по умолчанию максимум 20 МиБ на входящий файл. Старое обещание 1,5 ГБ удалено: такой режим требует отдельного локального Bot API и соответствующих лимитов. Встроенное Compose-развёртывание локальный Bot API не содержит. `TELEGRAM_API_URL` предназначен для отдельно управляемого Bot API. Для режима `--local` также нужны `TELEGRAM_LOCAL_FILE_ROOT` и read-only mount его файлов.
- Проверяются заявленный и фактически скачанный размер; FFmpeg имеет ограничение размера результата, длительности и времени работы. Неправильные файлы не переименовываются в MP3. Загрузки YouTube и транскрипция могут зависеть от региональных ограничений, доступа провайдера и квот.
- По умолчанию одна активная задача, 100 заданий в очереди, не более трёх незавершённых заданий на пользователя. `JOB_TIMEOUT_SECONDS=1800` ограничивает одну попытку; у subprocess свои меньшие таймауты. Частичные файлы очищаются при обычной ошибке/отмене.
- Telegram initData действуют час; после истечения пользователь повторно открывает Mini App. Аудио и DOCX требуют заголовка авторизации так же, как JSON API. Произвольные ссылки на аудио без авторизации не работают.
- Идентификаторы моделей настраиваются; доступность выбранного Gemini/OpenRouter необходимо проверить с реальным аккаунтом перед выпуском. Ошибка AI не маскируется успешным пустым конспектом.
- Аудио передаётся Gemini, транскрипт — настроенному провайдеру конспектирования. Загруженные Gemini-файлы удаляются после обработки; неудачное удаление отмечается в логах. Это не end-to-end encryption. Политику хранения и информирование пользователей должен определить владелец сервиса.
- Нет автоматического удаления конспектов по сроку: данные сохраняются до отдельно согласованного удаления. Контролировать рост volumes и хранить резервные копии вне VPS.

## Миграция существующих JSON

Сначала сделать копию старых JSON и аудио. Остановить прежний бот, чтобы два приложения не принимали одни обновления. Импорт явный, повторяемый, не изменяет оригиналы:

```sh
docker compose run --rm -v /absolute/legacy/data:/legacy:ro api python -m scripts.migrate_json /legacy
```

Записи без положительного `user_id`, с повреждённым JSON или несовместимой схемой отклоняются; скрипт сообщает имена и завершает работу с кодом 1. Владелец таких записей должен быть установлен вручную по достоверному источнику. Никакого общего доступа к записям без владельца нет. Импортированный ID не перезаписывает существующий конспект.

Аудиофайлы нужно отдельно перенести в volume `audio`, сохранив имена и права UID/GID 10001. Если старые записи не содержат `audio_url`, связь с аудио сама не угадывается. API выдаёт только файлы, явно связанные с конспектом владельца. Сверить количество импортированных записей и тестовую выборку по владельцам до переключения трафика.

## Резервное копирование и восстановление

Для согласованного снимка остановить **bot и worker**, оставив API читать данные. Остановка worker отменяет текущую обработку; она будет восстановлена после запуска. Скрипт использует SQLite backup API, поэтому нельзя заменять его простым копированием живого `.sqlite3` без WAL.

```sh
docker compose stop bot worker
# Выбрать новое имя; существующий архив скрипт не перезапишет.
docker compose exec api python -m scripts.backup /data/backup-2026-09-16.tar.gz
docker compose cp api:/data/backup-2026-09-16.tar.gz ./backup-2026-09-16.tar.gz
docker compose start bot worker
```

Перенести архив в защищённое внешнее хранилище и проверить checksum. Копия внутри `/data` не защищает от потери VPS; после внешнего сохранения убрать её штатной процедурой обслуживания. Архив содержит `data/slovech.sqlite3` и `audio/`; секреты и сертификаты в него не входят.

Восстанавливать сначала на отдельном экземпляре: проверить список файлов архива, распаковать **доверенный собственный** архив в пустые data/audio volumes, назначить UID/GID 10001, запустить API, выполнить `PRAGMA integrity_check` и проверить конспект, аудио, DOCX. Все старые процессы должны быть остановлены до замены production volumes. `.env` восстановить из защищённого источника отдельно. При запуске worker незавершённые задания могут обратиться к Telegram — не подключать тестовое восстановление к production-токену без намерения продолжить задачи.

## Обновление, откат, обслуживание

Перед обновлением сделать backup и сохранить предыдущий образ под неизменным `APP_VERSION`. Запускать новый выпуск через `APP_VERSION=release-N docker compose up -d --build`; проверять readiness и smoke-сценарии. Откат на предыдущий образ допускается только при совместимости схемы. При несовместимой миграции восстановить соответствующий backup вместе с аудио. `PRAGMA user_version` сейчас равен 1; неизвестные версии не принимаются. Команда `docker compose down -v` уничтожает volumes и не является процедурой обновления.

```sh
docker compose logs --tail=100 api bot worker
docker compose exec api python -m scripts.status
# Повторить конкретное failed-задание после устранения причины:
docker compose exec api python -m scripts.retry_job ID_ЗАДАНИЯ
# Только при остановленном worker; сначала просмотр:
docker compose stop worker
docker compose exec api python -m scripts.prune_orphans
# После проверки вывода, при необходимости:
docker compose exec api python -m scripts.prune_orphans --apply
docker compose start worker
```

`/health` — живость HTTP, `/ready` — доступность схемы БД. Worker имеет heartbeat healthcheck, а `scripts.status` выводит глубину очереди, возраст старейшего задания, свободное место. Настроить внешние оповещения о недоступности `/ready`, unhealthy worker, ненулевых `failed`, длительном ожидании задач, заполнении диска. Compose healthcheck сам по себе не перезапускает unhealthy-процесс; `restart: unless-stopped` относится к завершению процесса. Логи ограничены по размеру и не содержат тел запросов, транскриптов и провайдерских ответов; идентификаторы запросов/задач позволяют сопоставлять ошибки.

## VPS с уже работающим nginx

`deploy/compose.vps.yaml` сохраняет существующий HTTPS reverse proxy и публикует API только на `127.0.0.1:18000`. Caddy в этом варианте отключён профилем. Запускать `docker compose -f compose.yaml -f deploy/compose.vps.yaml …`, затем переключить `proxy_pass` nginx на `http://127.0.0.1:18000` и выполнить `nginx -t` перед reload. Доверенный адрес forwarded-заголовков — gateway отдельной Docker-сети. Лимиты этого варианта рассчитаны на ограниченный VPS; необходимо наблюдать RSS, swap и время очереди. Один CPU и менее 1 ГБ RAM ограничивают пропускную способность, особенно при конвертации.

Если используется существующий локальный Telegram Bot API, задать `TELEGRAM_API_URL=http://host.docker.internal:8081`; host gateway настроен для bot/worker. На текущем VPS Bot API работает в режиме `--local`: используются `TELEGRAM_LOCAL_FILE_ROOT=/var/lib/telegram-bot-api`, read-only mount и UID 101 worker, совпадающий с владельцем файлов API. Для совместной записи в volumes задать `STORAGE_GROUP_WRITABLE=true`: группа 10001, директории 2770, umask 0007. Пути из Telegram проверяются на принадлежность разрешённому корню. На другом VPS проверить UID владельца файлов или убрать переопределение user/mount для публичного API. Сам сервер Telegram Bot API управляется отдельно.
